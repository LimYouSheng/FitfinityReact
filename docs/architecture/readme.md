# How the system fits together

[Code owners and feature map](../code-owners.md) · [System and verification diagrams](diagram.md) · [Current rules and dated history](../service_contracts.md)

**Staff interface.** React/Vite renders the Owner, Admin and Trainer portal. Feature screens use injected asynchronous services; `PortalDataProvider` owns authorized snapshots and `useAppNavigation` owns account-scoped history. Explicit demo mode uses prototype data and browser storage. API mode uses `apiPortalAdapter` and FastAPI without falling back to mocks. GitHub Pages hosts the separate demo export. A session-scoped recovery panel above the routes exposes uncertain simple-form commands after their editors close; the adapter retains immutable intents and the server owns receipts.

**Editor and recovery ownership.** UI drafts, submitted commands and post-save reads have separate lifetimes. The following maps the current implementation; [Service Contracts](../service_contracts.md#part-1--current-system-rules) owns the business invariants. `SessionsRoute` selects the session list, permitted detail or pending recovery in the established acknowledgement → summary → outcome → plan → change order. It preserves session-record keys and login-generation recovery keys. `App` retains global navigation, authentication and profile recovery. `apiBackedWorkflows` identifies API orchestration; individual capabilities still gate writes.

| Transition | Implementation owner and retained behavior |
| --- | --- |
| Idle → opening review → editing | Feature control captures an enabled record lifetime through `useReviewLifetime`; a retired response cannot claim a later editor. This helper is shared only by the matching lifecycle controls. |
| Editing → same-scope refresh | `ApiSessionDetailsRoute` retains the reviewed detail while the editor is active. Ordinary version changes do not silently replace the draft; the server checks its reviewed version when saving. |
| Editing → authority/identity retired | Session selection/detail scope checks retire stale private state. A transient read failure can retain authorized detail; an access denial cannot. Scope rules remain feature-specific. |
| Editing → confirmation → continue/cancel | `ActionConfirmationProvider` binds each decision to its caller; replacement, unmount, session end or the caller’s abort retires that decision. `EditGuardProvider` owns navigation confirmation and unsaved-draft discard. |
| Confirmed → submitting → rejected/unknown/committed | Domain service adapters own the command. `reconciledCommand` is the shared owner for matching simple commands, retaining the original body, key and login generation; other domain adapters keep their specialized semantics. Closing UI does not undo a sent command. |
| Unknown → explicit Check / confirmed retry | Recovery reads the original receipt. Check never posts; an explicit retry may reuse the original immutable command only after reconciliation and current authority checks. Background snapshots expose pending work without consuming it. |
| Committed → refreshing → displayed / refresh failure | The feature retains successful-save status. A failed follow-up read offers refresh recovery, not another save. `ApiSessionDetailsRoute` owns this boundary for session details. |
| Session ended → UI retired | Login generation and authority guards remove old private UI/commands from the current session. This neither rolls back server commits nor claims recovery across browser restarts. |

Keep those owners separate when extracting routes. Regression evidence spans the confirmation/edit-guard tests, command/recovery tests, session-detail tests and real-API refresh, lost-response and permission scenarios; full CI remains the acceptance gate. The existing shared review guard does not replace record-specific draft retirement or transaction/receipt logic.

**Identity and application.** Cognito owns staff identity and authentication challenges. FastAPI verifies signed tokens, cookies/CSRF, active staff identity and current record permissions. Domain services recheck reviewed versions, assignment and conflicts inside the transaction. Browser capabilities describe available features; they do not grant authority.

**Durable storage and recovery.** PostgreSQL owns relational business records, purchased snapshots, audit/credit evidence and command receipts; SQLAlchemy and Alembic define models and forward schema changes. A command commits its effects and receipt together. A lost response is reconciled using the original actor and key. S3 is the selected durable media boundary; media and report workflows remain subject to the operation matrix. Application memory and local disk are not durable business stores. Package lifecycle storage separates live bookings from stable session identities and typed deletion archives, preserving plans, results and decision history. Stable original/performed Trainer evidence and append-only assignment history are source-accepted; current assignment remains compatible with the outgoing application. Historical session access never grants current write or full client-profile authority. Permitted package deletion Undo restores original identities with increasing versions only after checking unchanged records and original media availability. General Undo uses typed immutable change snapshots, dependency hashes and compensating transactions; acceptance remains governed by the operation matrix.

**Hosting and portability.** The selected AWS topology serves static assets through CloudFront and routes API Gateway requests to FastAPI on Lambda through the Lambda Web Adapter. Cognito, private PostgreSQL/RDS and S3 have distinct responsibilities. The application remains ordinary container-compatible HTTP so hosting changes do not require rewriting business logic. Selected topology does not establish that current source is deployed; Progress owns observed deployment status.

**Protected media.** Library saves reserve a private original intent, upload immutable bytes directly with short-lived signatures, verify stored length/type/checksum and recheck current permissions/version before publishing metadata and receipts atomically. Reads verify bytes and recheck attachment scope before playback. Durable cleanup waits for upload leases and live references, retaining work across failures. Session recordings use the same private storage boundary, with reviewed session/plan ownership, a fixed publication expiry and durable abandoned-upload/replacement cleanup. Production media is disabled by default; source acceptance follows the matrix, while processing/transcoding and worker scheduling remain separate work.

**Testing.** Playwright's `tests-api/` runs the real frontend, FastAPI routes, migrations, JWT checks, cookies, CSRF and authorization against temporary Docker PostgreSQL with worker-isolated databases. A local signed-token provider substitutes Cognito. The media tests use real object IO against a pinned, disposable RustFS S3-compatible service with private per-worker buckets; this does not establish AWS S3 acceptance. The verifier rejects non-test database/storage targets and removes owned resources. CI distributes the complete real-API inventory across two isolated shards; a required aggregate compares case identities and requires both jobs to pass without retries or omissions. Node-simulator browser tests remain separate frontend evidence. Separate backend drills kill actual HTTP workers before/after a commit, restart against the same isolated database and verify rollback, durable receipts and authentication. The operator recovery drill exercises real identity-revocation triggers with SDK-stubbed Cognito reset responses; the app gains no recovery-admin powers. No Lambda deployment or production database is needed.

**Delivery and hardening.** The Docker `application` stage is shared; `test` adds test dependencies without downloading the Lambda adapter, while `runtime` adds the pinned adapter. Final-head frontend/backend/API-browser CI precedes source acceptance. Normal main verification/demo publishing is independent of AWS image approval. Image publication is manually initiated with an exact main SHA, reruns all three gates for that SHA, and then requires the protected AWS environment approval; it never deploys Lambda. Image publication, migrations, deployment and live/provider/device acceptance require their own evidence and applicable authorization. Mutation testing, measured performance budgets and OpenTelemetry/Grafana remain planned work in Progress, not existing capabilities. [Service Contracts](../service_contracts.md#deployment-migration-and-acceptance) owns release safeguards.

**Full verification suite.** Existing checks cover frontend units; simulator browser workflows; backend/PostgreSQL transactions, authorization and migrations; real-API browser persistence/recovery; offline infrastructure guards; assessment paper-form parity; lint/source health and verifier regressions; and builds/PWA behavior. These have different evidence scopes: simulator success does not prove persistence, and synthetic identity does not prove real Cognito. The [suite diagram](diagram.md#full-verification-suite) separates existing checks, planned additions and external acceptance. README owns executable commands; Progress owns results and remaining work.

**Planned mutation and performance testing.** Mutation testing will target critical JavaScript/Python business rules, authorization and persistence, inspect surviving/equivalent mutations and establish justified gates. Performance campaigns will measure p50/p95/p99 latency, throughput, errors, CPU/memory, connection/query behavior and browser vitals with representative data, concurrency and bounded overload/fault cases. Cold/warm measurements need an identified environment; local Docker cannot prove Lambda cold-start behavior. Establish measured budgets after baseline rather than copying arbitrary thresholds. Expanded resilience testing will cover rate limits, dependency failures, broader service failures and interrupted-write recovery alongside existing targeted process-restart cases.

**Planned observability.** OpenTelemetry will correlate traces, metrics and structured logs across requests, database work and recovery. Grafana dashboards, SLOs and actionable alerts will use those measurements. Redaction of health/identity data, credentials, cookies and SQL parameters, plus sampling, retention, cardinality and cost controls, must precede activation. Validate correlation and exporter failure isolation locally first; instrumentation and export should start disabled. A Grafana stack, ingestion, credentials and production activation remain separately scoped work, not a connected capability today.

**Supply-chain and planned security maintenance.** Dependabot source configuration covers bounded weekly npm, GitHub Actions and Dockerfile-image update PRs; the remaining floating frontend tooling declarations are pinned to their existing lockfile versions. Bot PR execution has been observed; complete GitHub alert inventory/settings remain unverified because alert reads return403. Required npm audit includes development tooling, blocks high/critical findings and retains the report; it does not cover Python or container packages. Python custom hashed locks and Compose image pins still require manual maintenance until a compatible updater is tested. [Runbook](../runbook.md#dependency-maintenance) owns review/triage instructions; Progress H4 owns remaining coverage. Assess SBOMs and artifact/source provenance against verified digests. Secret scanning and static security analysis supplement current lint and authorization tests; repository/account-level settings need verification before any claim they are enabled. Automated updates or clean scans do not replace review, full CI or release approval.

**Planned production operations.** Consolidated AWS release preparation will bind source, image/artifact, grants and migrations to a reviewed rollout and populated-data recovery plan. Health/readiness acceptance, synthetic monitoring, incident ownership, alert exercises, rollback, backup/restore and migration-recovery drills will establish measurable recovery limits. Capacity/resource/cost monitoring supports those decisions. Start with isolated drills; actual AWS changes, real providers, paid telemetry and live load require their applicable authorization. These tasks belong to [M10 work packages](../../PROGRESS.md#m10-work-packages--planned) under Progress → Remaining work. M10 does not defer the security, migration and restore evidence required before launch.
